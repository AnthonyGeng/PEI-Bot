# PEI Bot 技术设计

本目录是 PEI Bot 底座的技术设计,主要读者是北京开发团队和 Coding Agent。能被机器校验的部分(清单格式、契约接口)放在 `contracts/` 下,设计说明放在这里。

可行性分析与决策过程见:https://claude.ai/artifact/XSxmyUMZahT1Zy1w57RXgq (私有,需由所有者分享)

## 第一版范围

第一版只做底座空壳和 Admin 管理界面:Admin 控制面、User 网关、宿主池、前端外壳和插件的上传、加载、回滚。除内核外,所有功能都以插件形式交付,包括数据权限(Brand Scope)和主数据。第一版不做 Bot 功能;Bot 以后作为插件加入,不改内核。

| 第一版做 | 第一版不做 |
| --- | --- |
| Admin:插件上传、版本与通道、宿主池分配、排序、回滚;用户与角色、插件访问权限、功能开关;审计查看 | Bot 界面、线程、值班台 |
| 网关:GIP 登录、权限、路由、按池熔断、审计 | 模型网关、Decision 1、工具注册表 |
| 宿主池:插件加载与升级、故障隔离、资源上限 | Bot 运行时与审批卡片 |
| 前端外壳:8 个外壳插槽、扩展点机制、错误边界 | Google Chat、Gmail 渠道 |
| 内核调度服务、事件、数据库迁移与视图授权 | |
| 1–2 个示例插件,用于验证上述全部能力 | |

清单里的 `tools` 和 `requiresFeatures` 字段保留。第一版的业务插件可以照常声明工具,内核只登记不启用;等 Bot 插件上线,这些工具直接可用,不用回头改插件。

## 已确认的决定

| 决定 | 内容 | 出处 |
| --- | --- | --- |
| 底座 | 以北京团队的"PEI 全栈插件化应用平台"为主干,PEI Bot 内核即其纯技术内核 | 可行性文档第 14 节 |
| 后端语言 | 统一 .NET;前端为 ESM | 第 14.5 节 |
| 进程结构 | Admin 控制面;User 拆为网关(内核,不加载插件)和宿主池(加载插件) | 第 14.3 节 |
| 宿主池 | 同一镜像、不同插件清单;起步三个:core、trade、experimental | 第 14.3 节 |
| 数据库 | 每插件一个 schema 和独立数据库角色;跨插件只读走带版本号的视图 | 第 14.4 节 |
| 后台任务 | 由内核调度服务(Cloud Scheduler + Cloud Tasks)回调,插件不自建线程 | 第 14.4 节 |
| 模型选择 | 管理员强制 > 所有者指定 > Gemini Decision 1;Decision 1 登陆 Vertex 前由 Flash-Lite 兜底 | 第 5 节 |
| 入口 | 网站独立运作;Google Chat、Gmail 为可选渠道,第二阶段再做 | 第 4.4 节 |
| 外部用户 | B2B 客户和大陆供应链用户暂不使用 Bot,由 `bot` 功能开关控制 | 第 14.9 节 |
| 范围 | 暂缓电脑操作和录屏教学;先到 30–50 人试点 | 第 13 节 |
| 版本范围 | 清单中的版本范围统一用 NuGet 写法,如 `[1.0,2.0)` | 01 号文档 |
| 第一版身份 | 管理员创建的本地账号;插件只见内部用户 ID,之后迁到 GIP 对插件透明 | 02 号文档 |
| 数据库 | 云上 Cloud SQL for PostgreSQL;本地开发用自建 PostgreSQL,大版本、扩展、角色模型、时区与云上一致 | 08 号文档 |
| 数据库迁移 | 由 Admin 在发布时执行一次;宿主只用无 DDL 权限的运行角色 | 03 号文档 |
| 时间 | 存储、传输、cron 一律 UTC;界面按用户时区显示;跟随当地钟点的任务可另填时区 | 01 号文档 |
| 实施顺序 | 第一版只做底座空壳并用示例插件验证;之后迁主数据和 PLM,WebOrder 最后;Bot 作为插件在第一版之后加入 | 本页“第一版范围” |
