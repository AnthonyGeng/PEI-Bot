# 04 身份与权限(草案 v0.1)

第一版的身份与权限要做到三件事:管理员能开账号、能决定谁用哪个插件、改动立即生效。同时为两件以后的事留好位置:迁到 GIP,以及外部租户。

数据表见 [`kernel/db/migrations/0001_identity_access.sql`](../../kernel/db/migrations/0001_identity_access.sql)。该脚本已在本地 PostgreSQL 上以 `pei_kernel` 角色连续执行两次,两次都成功(幂等)。

## 1. 概念

| 概念 | 说明 |
| --- | --- |
| 租户 | 第一版只有内部租户 `pei`。所有表现在就带 `tenant_id`,以后加外部 B2B 租户不用改结构 |
| 用户 | 内核分配的内部 ID。插件只见到这个 ID,看不到账号来自本地密码还是 GIP |
| 权限点 | 插件在清单里声明,发布时写入;全局写作 `插件id:名称`,如 `plm.techpack:techpack.read`。内核自己的权限点以 `kernel:` 开头。只增不删 |
| 角色 | 一组权限点,属于某个租户。用户可以有多个角色 |
| 插件启用 | 按租户开关。插件对某个用户可见,当且仅当它对该用户的租户启用,且该用户至少拥有它的一个权限点 |
| 功能开关 | 如 `bot`。对某个用户开启,当且仅当租户级开启,或用户属于该开关的放行角色 |

第一版不单独设计“插件访问权限”。有没有某个插件的权限点,就决定了能不能看到这个插件,少一个需要维护的概念。

数据权限(例如“只能看品牌 A 的款”)不在内核里。它由 Brand Scope 插件提供,内核只提供上下文值的传递机制。

## 2. 第一版的账号与登录

| 项目 | 做法 |
| --- | --- |
| 开户 | 只能由管理员在 Admin 中创建,不开放自助注册。系统生成临时密码,只显示一次,首次登录必须修改 |
| 密码 | 至少 12 位;用 ASP.NET Core Identity 的 `PasswordHasher` 存储;忘记密码由管理员重置 |
| 锁定 | 连续 5 次失败锁定 15 分钟,写审计 |
| 邮箱 | 全局唯一,不区分大小写。迁到 GIP 时靠邮箱把 GIP 身份关联到已有用户 |
| 会话 | 服务端会话。Cookie 里只放随机令牌(HttpOnly、Secure、SameSite=Lax),库里只存它的 SHA-256。禁用用户或强制下线立即生效 |
| 会话时长 | 应用端:闲置 12 小时、最长 7 天。Admin:闲置 30 分钟、最长 12 小时 |
| 多因素认证 | 第一版不做。Admin 前面加 Cloud IAP 作为第一道门;迁到 GIP 后由 Google 账号提供 |

**应用端和 Admin 用同一张用户表,但会话分开。** 只有拥有至少一个 `kernel:admin.*` 权限点的用户才能登录 Admin。

## 3. Admin 的权限与内置角色

| 内核权限点 | 允许做什么 |
| --- | --- |
| `kernel:admin.plugins.read` | 查看插件、版本、池分配和运行状态 |
| `kernel:admin.plugins.publish` | 上传插件到开发和试用通道 |
| `kernel:admin.plugins.promote` | 晋升到正式通道、回滚 |
| `kernel:admin.plugins.assign` | 分配宿主池、按租户启用插件 |
| `kernel:admin.users.manage` | 创建、禁用用户,重置密码,强制下线 |
| `kernel:admin.roles.manage` | 编辑角色和授权 |
| `kernel:admin.features.manage` | 管理功能开关 |
| `kernel:admin.secrets.manage` | 管理插件密钥 |
| `kernel:admin.audit.read` | 查看审计 |

| 内置角色 | 权限 |
| --- | --- |
| 平台管理员 | 全部 9 个 |
| 插件发布者 | 查看、上传到开发和试用通道 |
| 发布审批人 | 查看、晋升到正式通道、回滚 |
| 审计员 | 查看插件、查看审计 |

**发布与审批分开**:默认不允许把自己上传的版本晋升到正式通道。如果北京团队人手少到无法分开,可以在 Admin 设置里关掉这条限制,关掉这件事本身会写审计。

## 4. 权限怎么判断,改了怎么立即生效

1. **网关**在每个请求上算出该用户的有效权限集:用户所有角色的权限点之和,去掉未对其租户启用的插件。结果按“用户 + 访问控制版本号”缓存在 Redis 里。
2. 访问控制相关的任何一张表发生变化,数据库触发器都会把**访问控制版本号**加一。网关和宿主的缓存键里带着版本号,所以改动在下一个请求就生效,不需要等缓存过期。
3. 网关签发给宿主的内部令牌里带着用户 ID 和版本号。宿主按同样的键从 Redis 取权限集,在调用插件前装进 `IPermissionService`,所以插件里的 `Has()` 是同步的。
4. **前端外壳**启动时取一次当前用户的权限集,`ctx.can()` 是同步的。每个接口响应都带当前版本号;版本号变了,外壳重新拉取权限集并刷新导航。

## 5. 审计

以下事件由内核写入审计,插件无法关闭:登录成功或失败、账号锁定、修改或重置密码、创建或禁用用户、角色与授权变更、插件启用变更、功能开关变更、强制下线、Admin 中的所有发布操作。

审计表与插件共用,内核事件的 `plugin_id` 为 `kernel`。

## 6. 迁到 GIP

| 步骤 | 做法 |
| --- | --- |
| 1 | 在 Admin 中启用 GIP 登录,本地密码登录暂时并存 |
| 2 | 用户首次用 GIP 登录时,若 GIP 返回的邮箱已验证、属于公司域名,并且与某个已有用户匹配,就写入外部身份表,关联到该用户 |
| 3 | 全部用户关联后,关闭本地密码登录 |
| 4 | 保留一个本地应急管理员账号:密码离线保管,每次使用都告警 |

整个过程中用户 ID 不变,角色、权限和插件里的业务数据都不用迁移。

## 7. Admin 第一版的身份相关页面

| 页面 | 功能 |
| --- | --- |
| 用户列表 | 搜索、按状态和角色筛选 |
| 新建用户 | 邮箱、姓名、语言、角色;生成一次性临时密码 |
| 用户详情 | 角色、在线会话、禁用、重置密码、强制下线、该用户的审计记录 |
| 角色 | 列表;编辑时按插件分组勾选权限点,已弃用的权限点不显示 |
| 插件启用 | 按租户启用或停用插件 |
| 功能开关 | 按租户开关,并可设放行角色;对外部租户开启 `bot` 时必须填写法务评估结论 |
| 审计 | 按时间、用户、插件、动作查询 |
